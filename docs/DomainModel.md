# Domain Model

## Core Entities

### Requirement

Represents a business requirement that has been captured, reviewed,
approved and maintained throughout the project lifecycle.

#### Identity

- Requirement ID
- Title
- Description

#### Classification

- Requirement Type
- Priority
- Status

#### Ownership

- Business Owner
- Business Analyst
- Technical Owner

#### Lifecycle

- Version
- Created Date
- Last Updated
- Approval Status
- Approved By
- Approval Date

#### Traceability

- Source Documents
- Related Decisions
- Related Requirements
- Related User Stories
- Related Test Cases
- Related Risks


### Document

Represents a source of project information.

Properties

- Document ID
- Name
- Type
- Version
- Upload Date
- Author


### Decision

Represents a project decision.

Properties

- Decision ID
- Description
- Decision Maker
- Decision Date
- Reason
- Supporting Evidence


### Stakeholder

Represents a project stakeholder.

Properties

- Stakeholder ID
- Name
- Role
- Team
- Email


### Test Case

Represents a test case linked to one or more requirements.

Properties

- Test Case ID
- Name
- Status
- Owner


### Risk

Represents a project risk.

Properties

- Risk ID
- Description
- Owner
- Severity
- Status


### Approval

Represents a formal decision by an authorised stakeholder
to approve, reject or request changes to a requirement.

Properties

- Approval ID
- Requirement ID
- Requirement Version
- Approver
- Decision
- Date
- Comments


# Relationships

- A Document can contain many Requirements.
- A Requirement can originate from many Documents.
- A Requirement can have many Decisions.
- A Requirement can have many Approvals.
- A Requirement can have many Test Cases.
- A Requirement can have many Risks.
- A Decision can reference many Documents.
- A Stakeholder can own many Requirements.
- A Stakeholder can provide many Approvals.
- Each Approval relates to a specific Requirement version.

## Data Modelling Principle

ReqPilot will maintain a structured core model for information that
is common and important across requirements, while allowing
additional requirement-specific information to be retained without
requiring changes to the core data model.

No source information should be discarded solely because it does not
fit an existing predefined field.

Where AI identifies potentially relevant information that cannot be
confidently mapped to the existing model, it should be retained and
flagged for human review.

### Task Versioning

A Task has a stable Task ID and maintains version history.

The Task entity identifies the work item. Each Task Version records the task's details and status at a particular point in time.

#### Task Version Attributes

- Task ID
- Task Version
- Task Name
- Task Description
- Status
- Priority
- Size
- Assigned To
- Due Date
- Created At
- Created By
- Change Summary

Task ID and Task Version together uniquely identify a Task Version.

#### Version Creation and History

The original AI-generated Task Version must be preserved and must not be overwritten.

When a reviewer edits a Task, ReqPilot creates a new Task Version. The new version records the revised details and the appropriate status.

Each version must retain its creation context, including whether it was generated by AI or modified by a human. Review outcomes, reviewer identity and review timestamps must also be traceable.

Historical Task Versions remain available for audit and traceability.
